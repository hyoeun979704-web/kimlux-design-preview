태닝보다 무서운 건??

가방이 도착하고 감정이 시작되자, 고객님은 아기 재우고 내 상품 화면을 들여다보는 게 소소한 낙이 되셨대요.
날짜 코드 위치와 각인 서체까지 보고 정품 확인을 마쳤어요.
캔버스는 모서리까지 까진 곳 없이 멀쩡했고, 지퍼도 걸림 없이 부드러웠어요.

고객님이 제일 걱정하신 건 손잡이 태닝이었어요.

그래서 저희도 여기까지는 걱정하지 않았는데요.

손잡이를 뒤집어 연결 탭 쪽을 보니 가죽이 실처럼 갈라져 있었어요.
가방을 들 때마다 무게가 실리는 자리라, 그대로 두면 더 벌어질 수 있는 곳이에요.

그래서 바로 팔았을까, 맡겼을까???

맡기실 때 제일 많이 물으시는 게 이거예요.

상태를 좋게 보이도록 미화하지 않는 게 김럭스 원칙이거든요.

2. 핵심 설계

원고 품질을 정하는 입력은 프롬프트보다 근거 원장이다. 원장은 채팅 원문, 공식 약관, 광고 지표에서 뽑은 사실과 조건을 출처와 함께 담는다. 원고의 사실 문장과 경험 문장은 모두 원장 항목 ID를 가져야 하고, ID가 있다는 것만으로 통과하지 않는다. 연결된 근거가 그 문장을 실제로 뒷받침하는지 따로 판정한다(8절).

수집 경로의 제약

실측 결과 두 메신저 모두 서버에서 바로 읽는 경로가 없다.

원천 현재 경로 제약

카카오톡 CSV 내보내기 또는 kakao-ax dump 로컬 전용. 창을 열 때 포커스를 뺏으므로 사용자가 쓰는 중에는 막힘

v1 입력은 메시지 묶음 업로드 API로 통일한다. 로컬 도구, 내보내기 파일, 직접 붙여넣기가 모두 같은 형식으로 들어온다. 엔터메세지 서버 조회는 사내 권한과 보안 정책이 정리되면 담당자가 어댑터로 붙인다.

{
  "source": "kakao | enter_message | manual",
  "room_id": "kakao_entnext_marketing",
  "room": "엔터넥스트 마케팅",
  "captured_at": "2026-11-05T17:00:00+09:00",
  "range": {"from": "2026-11-05T09:00:00+09:00", "to": "2026-11-05T17:00:00+09:00"},
  "coverage": {"status": "complete | partial", "queried_from": "...", "queried_to": "...", "traversal_complete": true, "limit_reached": false, "limit_reason": null, "verified_by": "tool | 담당자 ID"},
  "messages": [
    {"sender": "표시 이름", "sent_at": "2026-11-05T11:54:00+09:00", "text": "원문", "attachments": [{"sha256": "...", "mime": "image/png", "filename": "...", "storage_ref": "..."}]}
  ]
}

source, room_id, captured_at, range, coverage, messages, messages[].sent_at, messages[].text(첨부만 있으면 빈 문자열)는 필수다. messages는 빈 배열일 수 있다. room_id는 담당자가 등록한 고정 ID이며, 미등록 방은 격리한다. message_id는 시스템이 생성한다. manual 원천의 발신자와 시각은 입력자 진술이므로 unverified로 두고, 방 이름이나 표시 이름만으로 클라이언트 직접 지시로 승격하지 않는다.

첨부 이미지는 가림 처리 후 저장한다. 이번 조사에서도 핵심 지시가 스크린샷으로 전달됐다. 이미지 안의 글은 OCR 결과와 이미지 ID를 같이 저장하고, 사람이 확인하기 전에는 unverified로 둔다. 가림을 끝내지 못한 첨부는 LLM에 보내지 않는다.

처리 규칙

  • 중복 키: sha256(source + room_id + sender + sent_at + text + attachment_hashes).
  • 처리 순서: 수신 → 가림(텍스트·첨부·OCR) → 영구 저장 → LLM 전달. 이 순서를 바꾸지 않는다.
  • 가리는 항목: 비밀번호, 접근 코드, 토큰, 계좌번호, 전화번호, 고객 개인정보. 가림 내역과 오류 로그에는 값이 아니라 종류와 위치만 남긴다.
  • 원문 열람 권한, 보존 기간, 삭제 범위는 13절 협의 항목이다. 정해지기 전에는 실제 고객 메시지를 넣지 않는다.
  • 채팅·OCR·인용문은 비신뢰 데이터다. 원문에 적힌 지시를 실행하지 않고, 추출 모델은 후보만 제안한다. "공개 승인됨" 같은 원문 문장으로 검증 상태·공개 범위·권한·규칙을 바꾸지 않는다. 이 값은 인증된 검토자만 확정한다.
  • 내부 잡담, 단가 논의, 내부 인물 평가는 internal_only로 표시하고 근거 추출에서 제외한다.
  • 수집 범위를 넘는 공백은 coverage_gap으로 기록한다. 50건 제한 때문에 빠진 기간을 "지시 없음"으로 처리하지 않는다.

체크포인트 전진 규칙

연속성은 메시지가 처음 나타난 시각이 아니라 조회 범위로 판정한다. 메시지가 뒤늦게 시작돼도 그 앞을 다 조회했다면 공백이 아니다. 어댑터는 queried_from, queried_to, 탐색 완료 여부, 제한 도달 여부를 돌려준다. 확인할 수 없으면 traversal_complete=false로 둔다. 창에 불러온 구간만 읽는 카카오톡 덤프와 약 50건 캐시를 읽는 엔터메세지 도구가 여기에 해당한다.

경우 판정 checked_until
도구 수집, traversal_complete=true, limit_reached=false complete. 메시지 시각과 무관 queried_to까지 전진
도구 수집, limit_reached=true 또는 traversal_complete=false partial로 강제. 확인된 조회 구간 밖을 coverage_gap으로 기록 전진 안 함
complete이지만 range.from이 현재 checked_until보다 뒤 사이 구간을 coverage_gap으로 기록 전진 안 함
겹친 재업로드 메시지는 중복 키로 제거 연속 구간의 최대 range.to까지 전진
빈 구간, messages=[], complete, 인증된 담당자가 verified_by로 확인 메시지 없음으로 인정 range.to까지 전진
빈 구간, 담당자 확인 없음 partial 전진 안 함
manual 입력 담당자의 범위 확인이 있을 때만 complete 확인 범위까지 전진

한 번 기록된 coverage_gap은 채워지거나 범위가 맞는 checkpoint_ack가 있을 때만 닫힌다.

5. 근거 원장

{
  "id": "ev_01",
  "version": 1,
  "content_hash": "sha256(statement, quote, scope, public_use, condition, values)",
  "type": "client_directive | operating_condition | reference_fact | metric | persona_hypothesis",
  "statement": "매입 광고 문구는 5분 입금 대신 당일 감정, 당일 입금으로 조정",
  "quote": "원문 그대로",
  "source_ref": {"message_id": "...", "url": null},
  "said_at": "2026-10-13T15:00:00+09:00",
  "scope": {"service": "buyback", "channel": ["ads"]},
  "authority": "client | internal | official_doc | unknown",
  "verification_status": "candidate | verified | conflict | rejected",
  "public_use": "allowed | conditional | blocked | internal_only",
  "condition": null,
  "values": [{"item": "위탁 기간", "value": "90", "unit": "일", "qualifier": "최대"}],
  "open_issue": "운영 적용 범위 미확정",
  "verified_by": null,
  "verified_at": null,
  "expires_at": null,
  "superseded_by": null
}
  • quote가 원문에 정확히 포함되지 않으면 등록을 거부한다.
  • 원고 입력 조건은 verification_status=verified, public_use가 allowed 또는 conditional, open_issue=null, superseded_by=null, 유효기간 내, 범위 일치를 모두 만족하는 것이다. conditional이면 condition이 비어 있을 수 없다.
  • conditional은 검증된 사실에 실제 이용 조건이 붙는 경우만 뜻한다. "확인 필요"는 조건이 아니라 open_issue이며, 관련 주장 생성을 막는다.
  • scope를 지킨다. 광고용 지시를 블로그에 쓰려면 사용 범위 확인이 필요하다.
  • 채널 값은 naver_blog, ads, instagram만 쓴다. 프로필, 근거, 동의, 규칙, 테스트가 같은 값을 쓰고 범위는 정확히 일치해야 한다. 다른 표기는 등록을 거부한다(E_CHANNEL_INVALID).
  • 운영 조건에는 만료일을 둔다. 시작값은 30일이다. 만료된 항목은 원고에 쓰기 전에 다시 확인한다.
  • 경험은 evidence가 아니라 7절의 case_record로 확인한다. evidence.type에 경험 값은 없다.
  • reference_fact는 업계·용어 같은 일반 사실의 근거다. 공식 문서, 기관 자료, 인증된 검토자의 확인 중 하나가 필요하다.
  • 내용이 바뀌면 같은 항목을 덮어쓰지 않고 version을 올린다. 만료일만 연장하면 content_hash와 version은 유지한다. 재확인 시각은 기록한다.

사례 기록

원고의 경험 문장은 case_record에 연결된 내용만 쓴다. 검증 조건은 네 가지이고 하나라도 빠지면 사례 문단을 생략한다.

{
  "case_id": "case_01",
  "version": 1,
  "subject": "물건·상황",
  "witness_role": "담당 감정사 | 수선 담당 | 고객 본인",
  "event_confirmation": {"confirmed_by": "확인자 ID", "confirmed_at": "...", "fact_ids": ["cf_1"]},
  "consent_id": "consent_01",
  "compensation_relation_id": "comp_01",
  "facts": [{"id": "cf_1", "subject_service": "buyback", "quote": "원문 그대로", "message_id": "...", "values": [{"item": "수선 기간", "value": "3", "unit": "일"}]}]
}

공개 동의는 별도 객체로 둔다. 인증된 검토자가 확정한다.

{
  "consent_id": "consent_01",
  "version": 1,
  "case_id": "case_01",
  "consented_by_role": "고객 본인 | 담당자",
  "allowed_channels": ["naver_blog"],
  "allowed_fact_ids": ["cf_1"],
  "anonymization": {"blocked_terms": ["고객 이름", "지점명"], "forbid_exact_amount": true},
  "status": "granted | withdrawn",
  "source_ref": {"message_id": "..."},
  "confirmed_by": "...",
  "confirmed_at": "...",
  "expires_at": null
}
  • facts[].message_id는 실제 source_message를 가리켜야 하고, quote는 그 메시지 원문에 정확히 있어야 한다. 아니면 사실 등록을 거부한다(E_CASE_QUOTE_NOT_FOUND).
  • facts[].subject_service는 검토자가 사건 확인 때 확정하고, 사례의 content_hash에 넣는다.
  • 원고에 쓸 수 있는 사실은 event_confirmation.fact_ids에 있는 것뿐이다. 사건 자체가 확인됐어도 확인 목록 밖의 결과·감상은 쓰지 않는다.
  • case_fact_ids는 동의의 allowed_fact_ids 안에 있어야 한다. 원문에 있는 사실이어도 허용 목록 밖이면 차단한다. blocked_terms와 forbid_exact_amount는 독자용 문장에서 결정적으로 검사한다.
  • 문장 단위로 facts ID를 연결한다. 인물, 행동, 결과, 감상을 원문보다 넓히면 차단한다.
  • 답변 인용이 채팅에 있다는 사실은 실제 사례의 증명이 아니다. 담당자의 사건 확인이 별도로 필요하다.
  • FAQ·약관 근거로 고객 경험을 쓰지 않는다. 경험을 connective나 reference_fact로 분류하지 않는다.
  • 답이 "없음"이면 사례 문단을 만들지 않는다. 제목·태그·CTA도 같은 검사를 받는다.

질문서 규칙

  • 질문은 항목별로 required 또는 optional이다. 상태는 open, answered, verified, unavailable, conflict 중 하나다.
  • verified 근거로 답할 수 있는 항목은 질문하지 않는다. candidate나 conflict 기록은 답으로 치지 않고 "이 기록이 맞습니까" 형태의 확인 질문으로 낸다.
  • 한 회차의 질문은 최대 8개다. 필수를 먼저 넣고, 필수 안에서는 막힌 근거가 많은 항목부터 넣는다. 남은 질문은 다음 회차로 넘긴다.
  • interview_request는 원고당 1개이고 그 아래 interview_round를 둔다. 다음 회차는 현재 회차의 필수 질문이 모두 verified 또는 unavailable이 되고, S5 재실행에서 이월 질문이 남을 때 연다. 회차는 편당 2회까지다. 그래도 필수가 남으면 on_hold로 보내고 재브리핑을 요청한다.
  • 각 질문에 지금까지 찾은 근거와 왜 필요한지를 함께 적는다.
  • 시스템은 메시지를 보내지 않는다. 질문서를 만들고 대기한다. 전달과 답변 업로드는 사람이 하며, 전달한 사람이 sent_at을 기록한다.
  • 답이 오면 S1부터 다시 탄다. 답변도 일반 메시지처럼 원장에 들어간다.
  • 대기 시간은 해당 회차의 sent_at부터 잰다. 필수 항목에 새 답이 등록되면 그 시각부터 다시 48시간을 준다. 상한은 1회차 sent_at부터 7일이고 회차가 바뀌어도 초기화하지 않는다. 선택 항목의 답과 중복 답변은 시간을 늘리지 않는다. 계산한 마감은 interview_round.deadline_at에 저장한다. 필수가 남은 채 마감이 지나면 waiting_sources 중에도 on_hold로 바꾼다. 필수가 모두 충족된 뒤라면 마감을 적용하지 않는다. 수집이 끝났다는 사실만으로 on_hold가 풀리지는 않는다. 모두 시작값이다.

독자에게 노출되는 자유 문자열은 모두 text_unit에서만 나온다. 이 조건을 벗어나는 출력 키는 만들 수 없다. ending.url은 프로필 허용 목록과 대조하고, kind, type, placement는 열거값만 허용한다.

purpose, source_preference, id, unit_id, claim_kind, evidence_ids, case_fact_ids, subject_service, relation_ids, unresolved, required_output_mapping, speaker_unit_id, draft_id, version, mode는 출력에 없다. 빈 배열은 그대로 두고 null을 쓰지 않는다. 해시는 출력 객체 → 키 정렬·공백 없는 JSON → NFC → UTF-8 → SHA-256 순서로 계산한다. JSON에서 한글 등 비ASCII 문자를 \uXXXX로 바꾸지 않고, /도 이스케이프하지 않는다. 구분자는 ,와 :이며 앞뒤 공백을 두지 않는다. 언어 기본 직렬화가 이와 다르면 기준 해시(T87)와 맞지 않는다.

  • 표의 cells 수는 column_headers 수와 같아야 한다. v1은 다단 머리글과 칸 병합을 지원하지 않으며, 어기면 E_SCHEMA다.
  • topic_brief.covered_services는 이 글이 다루는 서비스 목록이다. 사실·경험 단위에는 subject_service가 하나 필수다. 두 서비스를 비교할 때는 서비스별 문장이나 표 칸으로 나누어 각각 그 서비스의 근거에 연결한다.
  • 판정 단위는 text_unit이다. unresolved가 비어 있지 않으면 S8을 통과하지 못한다.
  • 끝맺음은 정의 글에서 related_article 또는 information, 그 밖의 성격에서 cta다. 구조 규칙은 이 값으로 검사한다.

  • 기준 초안의 모든 단위를 정상 사례에 넣는다. 그 문장에 근거 없는 시점이나 조건을 보탠 변형(예: "정품이 아니면 접수 당일 반송합니다")을 위반 사례로 넣는다.
  • 위반을 통과로 판정한 건수는 0이어야 한다.
  • unknown은 위반을 놓친 것으로 세지 않고 human_hold 비율로 따로 기록한다.
  • 정상 사례의 통과 비율은 80% 이상, unknown 비율은 20% 이하여야 한다. 시작값이다. 전부 unknown을 돌려주는 모델은 이 기준에서 탈락한다.

  • 데이터: emphasis[] = {kind: "mark" | "bold", text}. text는 원고에 정확히 1번 나와야 한다. 아니면 emphasis_anchor_not_unique. 개수 범위를 벗어나면 emphasis_count.
  • 원고 원문(txt)에는 표식을 넣지 않고 별도 데이터로 둔다. 발행 담당은 이 목록대로 네이버 에디터에서 적용한다.

18.5 다음 주제 선정: 상위 노출 글 실측

  1. 후보 검색어마다 네이버 블로그 탭 상위 7편을 수집한다(제목, 본문, 이미지 수, 작성일, 블로그 ID). 수집일을 저장한다.
  2. 항목별 언급 편수를 집계한다: 상태·흠집, 시세·견적, 구성품·보증서, 방문·후기, 감정·정품, 접수 절차, 가방 유래. 분량·사진 중간값, 제목의 지역명·질문형 수.
  3. 키워드 정규식 집계는 1차 값이다. 보고서에 비율을 쓰기 전에 항목마다 2편 이상 사람이 읽어 확인한다. 근거가 약한 각도(보이백 금장: 7편 중 2편)는 공통점으로 쓰지 않는다.
  4. 김럭스 차별 축을 뽑는다. 1회차 실측(28편): 상태·흠집 86%, 시세·견적 82%, 구성품·보증서 75%, 방문·후기 71%, 감정·정품 64%, 접수 절차 54%, 가방 유래 43%. 분량 중간값 1,814자, 사진 약 14장. 유래 + 실제 감정 사례가 차별 축.
  5. 제목 규칙: 검색어를 앞에, 한 문장으로 주어와 서술이 맞아야 한다. 질문형 허용. 내부 용어·조어·사람이 안 쓰는 말 금지. 사용자가 "말이 안 된다"고 한 원 제목: "샤넬 보이백 매입, 클래식과 보는 곳이 다를까?" → title_unnatural(LLM 판정 + 사람 확인).
  6. 주제 카드 필드: 누가 찾나 / 상위 글 공통점(편수 포함) / 김럭스 글은 / 월 검색량 / 확인 필요(유래 출처, 실제 사례).

18.6 검토 화면(클라이언트 보고) 규격

  • 섹션 순서: 1 주제 선정(도식, 텍스트 최소, 채점은 원형 그래프) → 2 원고 → 3 다음 예상 주제(상위 글 공통점 + 카드 4개) → 4 네이버 기준(핵심 3장 + 걸러지는 글) → 5 담당자 체크리스트(체크박스).
  • 원고와 주석: 원고 문단마다 오른쪽에 주석 블록. 번호 표시와 주석 패널 별도 스크롤은 쓰지 않는다. 주석 = 종류(구조·내용·문장) + 제목 + 이유 + 네이버 근거 태그 + 확인 필요(빨강).
  • 색은 김럭스 사이트 CSS 변수에서 가져온다: --kl-green #1f4a46(메인), --kl-cyan #a7bcc0, --kl-green-muted #5a716e, --kl-red #b8432f, --kl-ink #0d0d0d, --kl-line #dfe4dc. 넓은 면에 크림 #fdffed를 쓰지 않는다(형광으로 보임). 배너 색을 추측해 쓰지 않는다.
  • 웹 기준: 최대 폭 1440px, 1280·1024px에서 재배치. 로고·번호는 Noto Serif Display, 본문 Pretendard.
  • 템플릿: rounds/template_v3.html, 빌드: rounds/build2.py 원고.txt 주석.json 템플릿 출력 강조.json 이미지.json. 빌드는 원고 글자가 txt와 같은지 대조한다.

18.7 작업 방식 회고

  • 확정한 지시를 다시 묻지 않는다. 출처로 확인되는 것은 확인하고 반영한 뒤 보고한다.
  • 비율·수치는 집계 방식(자동/사람 확인)을 함께 적는다.
  • 배포 후 공개 URL에서 반영을 확인한다. 중단된 명령도 일부 실행됐는지 확인한다(1회차 이미지 교체에서 발생).
  • 교차 검수(Codex)는 사용 한도로 11-12까지 미실시. 재개 시 이 절 규칙의 충족 여부만 확인한다.
